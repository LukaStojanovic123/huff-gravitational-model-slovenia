# Functional Gravitational Modelling of Service Catchments in Slovenia

Code repository for the paper:

> Stojanović, L., Drobne, S. and Lisec, A. Functional gravitational
> modelling of service catchments in Slovenia: a modified Huff approach
> with explainable machine learning assessment. *Applied Geography*
> (under review).

See [`CITATION.cff`](CITATION.cff) for the machine-readable citation, or the
[Citation](#citation) section below.

---

## Overview

This repository implements a modified Huff spatial-interaction model of
service catchments for Slovenia's 212 municipalities and 6,036
settlements, under two alternative weightings of municipal attractiveness
(a Gravitational Index built from 100 functional indicators, either AHP
expert-weighted or non-weighted). It compares the resulting catchments
against straight-line-distance and observed-commuting baselines, checks
whether a Random Forest can learn the same catchment pattern from the same
underlying features, and tests where model disagreement clusters
geographically. Every number quoted in the paper is reproducible from the
scripts in `src/`, run in order against the raw data described below.

---

## Study area and parameters

- Slovenia: 212 municipalities, 6,036 settlements
- Coordinate system: EPSG:3794
- Distance decay exponent: β = 2 (sensitivity tested at 1.5, 2.0, 2.5, 3.0 — see `config.py` for why 2)
- Network cutoff distance: 300 km (see `config.py` for why)
- All data collected in April 2026

## Setup

> **Before running any script, open `config.py` and set `DATA_RAW` to
> the path of your local raw data directory. This is the only file you
> need to edit.**

**Step 1 — Create environment**

```bash
conda env create -f environment.yml
conda activate huff_env
```

Conda is the tested and recommended path, specifically because
`environment.yml` pins the BLAS/LAPACK backend to OpenBLAS. On a CPU
without AVX-512 support, the alternative MKL build that conda would
otherwise install by default crashes natively (no Python traceback) the
first time certain code paths — `esda`'s spatial statistics, scikit-learn's
KMeans, SHAP's plotting — reach `scipy.linalg`. `pip` cannot pin a system
BLAS provider the way conda can, so installing via `requirements.txt`
carries a real risk of hitting this crash with no equivalent fix available
through pip alone:

```bash
pip install -r requirements.txt
```

See `docs/reproducibility_note.md`'s "Environment: a BLAS backend crash,
and why OpenBLAS is required" section for the full diagnosis, including
which specific statistic (Local Moran's I / LISA) turned out not to be
reproducible at all under the old MKL environment.

**Step 2 — Edit config.py**

```python
DATA_RAW = Path(r"your/path/to/raw/data")
```

**Step 3 — Run the pipeline**

```bash
python src/01_gi_construction.py
python src/02_road_network.py
python src/03_huff_ahp.py
python src/04_huff_nonweighted.py
python src/05_accessibility.py
python src/06_ml_framework.py --model AHP --sample-frac 1.0
python src/06_ml_framework.py --model NW --sample-frac 1.0
python src/07_beta_sensitivity.py
python src/08_euclidean_comparison.py
python src/09_entropy_uncertainty.py
python src/10_commuting_comparison.py
python src/11_export_outputs.py
python src/12_morans_lisa.py
python src/13_disagreement_synthesis.py
python src/14_ml_catchment_structure.py
python src/15_shap_dependence.py --model AHP
python src/15_shap_dependence.py --model NW
python src/16_spatial_layers.py
python src/17_data_audit.py
python src/18_output_manifest.py
```

The sequence runs 01 to 18 with no gaps. A script once occupied position
12 (`18_map_symbology_fields.py`, in an earlier numbering); its logic was
folded directly into `11_export_outputs.py` and the script itself
deleted, and every script from the old 13 onward was renumbered down by
one to close the resulting hole. Script filenames are numbered so that
running them in plain numeric order is always the correct dependency
order: each script's number reflects what it actually needs from earlier
scripts, not just where it happens to sit in the pipeline conceptually.
`11_export_outputs.py` in particular must run before `12_morans_lisa.py`,
since the LISA/Moran's I statistics are computed on the comparison maps
`11` builds — running scripts out of numeric order can silently compute
these statistics on a leftover map from a previous run (see
`12_morans_lisa.py`'s own `assert_map_is_fresh` check, which exists
specifically to catch that).

Rough run times on the original analysis machine, most expensive first:
`06_ml_framework.py` and `15_shap_dependence.py` both train a full-data
Random Forest over 1.28 million rows and are the two slowest steps in the
pipeline, typically tens of minutes each. `03_huff_ahp.py`'s road-network
Dijkstra search takes several minutes the first time it runs (cached to
`data/processed/` afterward, and reused by `04`, `07`, `08`).
`17_data_audit.py` independently rebuilds the road graph and reruns that
same Dijkstra search from scratch to audit it, rather than trusting the
cache, so it is also several minutes even though `03`/`05` themselves are
fast on a cached rerun. Every other script runs in well under a minute.
Scripts `03`, `04` and `05` accept a `--force` flag to recompute even if
their output already exists; without it, they skip straight to reporting
the existing file if one is present.

`06_ml_framework.py` and `15_shap_dependence.py` both accept `--model AHP`,
`--model NW`, or `--model both` (the default). Run each as two separate
invocations, as above, rather than `--model both`, on any machine with
limited RAM: each model on its own already holds a 1.28-million-row
feature table and a 100-tree Random Forest in memory, and training both
at once (in either script) is what exhausted this pipeline's 16 GB
analysis machine during testing and got the process killed by the
operating system with no Python error at all — this happened first in
`06_ml_framework.py`, then again in `15_shap_dependence.py`, since it
retrains its own pair of models independently of `06`'s. Both scripts
refuse to start a second instance of themselves while one is already
running (separate lock files in `data/processed/`), automatically clear
that lock if the process that created it is no longer actually running
(so a killed run doesn't permanently block every future one), and print
each model's own peak memory use at the end of its run.

## Data sources

Raw data files are not included in the repository, due to size and
licensing. Place them in the directory named by `DATA_RAW` in `config.py`.
`config.py` checks the contents of `DATA_RAW` against
`data/raw_manifest.json` on every run and prints a warning naming exactly
which file changed if anything has drifted since the manifest was frozen.

| File | Description | Source |
|---|---|---|
| `gis_osm_roads_free_1.shp` | OSM road network, all drivable classes (motorway through service/residential — see `02_road_network.py` for the full list) | OpenStreetMap via Geofabrik, April 2026 |
| `Municipalities_All_Groups_Weighted_AHP.gpkg` | Municipality layer carrying the pre-computed AHP-weighted Gravitational Index (`GI_AHP`) | GURS, OSM, SURS, ZZZS (combined into the GI by the same process documented in `01_gi_construction.py`, upstream of this repository) |
| `Municipalities_All_Groups_NotWeighted_Normalized.gpkg` | Municipality layer carrying the pre-computed non-weighted Gravitational Index (`GI_Final_NotWeighted`) | as above |
| `Municipalities_Points_normalized.gpkg` | Municipality centroids with the 100 individual normalised indicators the GI is built from | GURS, OSM, SURS, ZZZS |
| `Villages_points_real.shp` | Settlement centroids | GURS |
| `NA.shp` | Settlement polygons | GURS |
| `obcine_poligoni.shp` | Municipality polygons | GURS |
| `2023tabela.xlsx` | SURS 2023 commuting flow matrix | SURS (Statistični urad RS) |
| 86 facility layers, listed in `data/facility_layers.txt` | Individual service-facility point layers used for the accessibility indicators | OSM, GURS, SURS |

Both Gravitational Index layers (`GI_AHP` and `GI_Final_NotWeighted`) are
read by this pipeline as fixed inputs, not computed by it —
`01_gi_construction.py` independently recomputes the underlying rarity
weights as a cross-check against the reference table, but does not itself
build either GI layer from the 100 raw indicators.

## Note on the two Random Forest models

`06_ml_framework.py` trains two separate Random Forest models, not one
model reused twice: Model 1 predicts the AHP-weighted Huff model's
settlement-to-municipality probabilities, using `GI_AHP` as one of its 189
input features; Model 2 predicts the non-weighted Huff model's
probabilities, using `GI_Final_NotWeighted` (renamed `GI_NW`) instead.
Each model's own composite GI feature always matches the Huff variant it
is trained to predict — see `docs/ml_model_design_note.md` for a
correction this repository made to enforce that (an earlier version of
this script accidentally gave both models the AHP composite score).

**These Random Forest models are not a validation of the Huff model
against ground truth.** Both are trained to reproduce the Huff formula's
own output, not any independently observed catchment assignment — a high
R² here means the pattern the Huff formula produces is learnable from
municipality-level features and distance, not that the Huff model is
correct. The one comparison in this pipeline against genuinely independent
data is `10_commuting_comparison.py`, which checks the Huff model against
observed 2023 commuting flows.

A further, counterintuitive finding is documented in
`docs/ml_model_design_note.md`: when the composite-GI-feature bug above
was fixed, Model 1 vs. Model 2 agreement barely moved (80.78% → 80.86%),
even though the two models no longer shared any input column. The most
likely explanation is that both models rely overwhelmingly on distance
(63-69% feature importance) rather than the composite GI score, so
removing a shared input had little effect on where their predictions
land.
